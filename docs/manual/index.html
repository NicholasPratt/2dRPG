Adventure RPG Engine — Editor Manual

How to build a 2D action-RPG (SNES/GBA style) with the integrated editor: chapters, screens, sprites, enemies, NPCs, weapons, items, quests, and the combat feel.

For AI assistants: This manual is the authoritative source for answering user questions like “how do I make an enemy chase the player?” or “how do I make a quest that counts kills?” Each task is documented as a numbered recipe under How do I…?, and the concepts those recipes rely on are explained under Core concepts and Combat model. When the codebase contradicts this manual, the code wins — see RPG_Engine_Specification.md and code_base.md at the repository root. Terms in monospace are exact field/control names in the editor or data formats.

1. Overview

The engine renders top-down screens of 16×16-pixel tiles, 48×32 tiles per screen (768×512 px native). A game is made of one or more chapters; each chapter is a grid of screens linked north/south/east/west. The editor produces data files the runtime loads; runtime code never depends on the editor.

Reusable assets (characters, enemy types, NPC types, weapons, items, quest variables) live in a project-wide library (assets/game/project.adgame). Chapters reference those assets by id. Dialogue trees are chapter-specific. Every project is isolated under projects/<project>/.

2. Getting started & launching the game

Opening a project

On startup the editor re-opens the last project & chapter you worked on (remembered in projects/.editor_session); if that no longer exists it shows the Open Project modal. Pick an existing project + chapter, or type a new project/chapter name to create projects/<project>/ with its asset folders. The Project menu → Project Manager… lets you open, create, or delete projects at any time (deleting asks for confirmation and is permanent). Closing the editor or switching chapters/projects prompts you to save or discard unsaved work.

Saving

Saving a chapter does a lot at once: it writes the chapter file, flushes all edited sprites (metadata + sheet PNGs), exports each modified screen’s floor/wall/preview PNGs, and writes the project library (project.adgame). Sprite and screen-graphics edits are held in in-memory buffers during the session and only written on save.

Playing & testing

The editor launches the separate runtime window (adventure_game_window). There are three launch buttons (next to each scoped editor’s toolbar and under the Chapter menu):

ButtonStarts atStateUse when
Save and PlayChapter start screenNew game: state initialized from defaults; all placed enemies presentPlaying the game from the start
Play Selected ScreenThe screen selected in the Screens tabFresh: full HP, all placed enemies present, save untouchedIterating on the screen you’re editing
Play From Last EntryThe screen you last entered while playingFreshResuming a test where you last were
Every launch starts a new game. A normal launch initializes state from the project defaults — previously-defeated enemies and quest progress do not carry over from an earlier session, so all authored enemies always spawn. Progress is still written to save.adstate during play (and tracked in-memory across screen transitions within a session), but it is only re-loaded with an explicit --continue launch flag. The runtime records the last-entered screen + position in assets/game/test_checkpoint, which the “Play From Last Entry” button reads.

4. Core concepts

Chapters, screens & transitions

A chapter is a grid of screens. Each screen has a tile map (.admap) and N/S/E/W links to neighbours. Crossing a screen edge slides to the linked screen (when one exists and the destination entry isn’t blocked). Defeated-enemy and quest progress carry across screens via the game state registry.

Tile layers & collision

Each map has three layers: Floor (layer 0, walkable texture), Mid (layer 1, player-level, collision), and Ceiling (layer 2). Collision is binary: any non-zero mid-layer cell is solid. Wall art is painted in Edit Screen Graphics; the mid layer is the structural collision guide. Hazards (spikes, pits, timed spikes) live in the map and respawn the player at the map spawn.

Sprites & 8-direction animation

Sprites are authored in the Sprite Editor. Every frame has an action type (e.g. idle, walk, attack_1, hurt, dead, cast), a facing direction (E,W,N,S,NE,NW,SE,SW, or empty = any), and a duration in ms. Multiple frames sharing an action+direction loop as a clip. The runtime auto-mirrors: if there are no west-facing frames it flips the east ones (same for NW↔NE, SW↔SE). This direction system is identical for the player, enemies, and NPCs. The runtime drives action state automatically (idle/walk, attack/hurt/dead), so to make an animation appear you just provide frames with the matching action-type label.

Game state registry (quests)

A single runtime registry holds named integers, booleans, and item ownership. Everything quest-related routes through it: enemy kills, item pickups, money, dialogue conditions and actions. Variable names are entirely designer-authored (define them in Quest State) — there are no hard-coded quest names in the engine. Money is the integer variable Money by convention. Runtime progress is saved to save.adstate.

Persistence & respawn

Within a play session a defeated enemy stays dead — its id is recorded ("<screenId>/<enemyId>") and filtered out when that screen reloads, so it persists across screen transitions and respawns. Set a placement’s respawn flag (or a screen’s respawn enemies flag) to make it come back; quest counters and items behave the same way. Each launch is a new game: state initializes from defaults and the previous session’s save.adstate is not re-loaded (unless the runtime is launched with --continue), so authored content always appears.

5. Combat model reference

Combat aims for a 2D-Zelda feel with Metroidvania attack timing. Per-enemy-type tuning lives in Edit Enemy Types → Hit Reaction & AI; global feel constants live in the runtime (src/game/engine.cpp).

Player attacks

  • Melee (Z): a swing with windup → active hit-window → recovery. The hitbox only connects during the active window, and each enemy is hit once per swing. Range/damage/cooldown come from the equipped melee WeaponDef.
  • Ranged (X): fires a projectile using the ranged WeaponDef (speed, range, damage, ammo cost). Consumes ammo from the matching pool.

Hit reactions (enemies)

Damaging an enemy flashes it white, applies knockback in the hit direction (scaled by the type’s knockback resistance: 0 = flies back, 1 = immovable), and applies hitstun (the type’s hitstun seconds) during which it can’t move or attack. A lethal hit plays the dead state and fades out; a non-lethal hit plays hurt. The player is also knocked back away from whatever damages them.

Enemy attacks & AI

Each enemy type defines any number of attacks: Contact (damage on overlap), Melee (damage within range), or Ranged (fires a projectile at the player). Each attack has its own damage, range, cooldown, projectile speed, ammo sprite, and optional animation state. If a type’s aggro range is > 0, the enemy leaves its patrol to chase the player within that radius and, when the player escapes (past a hysteresis margin), walks back to the nearest point on its path and resumes patrol.

Projectiles & wall behavior

Projectiles know which side fired them: player shots hit enemies, enemy shots hit the player (both with knockback). Each ranged weapon’s On wall hit setting controls what happens at a wall:

BehaviorEffectExample
BreakVanishes on contact.Arrow, bullet
ReboundBounces off the wall, loses energy each bounce, then settles on the ground and fades.Slingshot stone

6. How do I…? (recipes)

Each recipe is a concrete sequence in the editor. These are the answers to most “how is this effect achieved” questions.

R1. Make an enemy chase the player

Screens → Edit Enemy Types → select the type → Hit Reaction & AI → set Aggro range > 0 (e.g. 120 px). The enemy will leave its patrol within that radius, chase, and return to the nearest point on its path when you escape. Set 0 to keep it strictly on waypoints.

R2. Make an enemy fly back / be immovable when hit

Same panel → Knockback resist. 0 = launched hard, ~0.7 = barely budges, 1 = immovable. Also raise Max HP above 1 so the reaction is visible before it dies.

R3. Make hits stagger an enemy (hitstun)

Same panel → Hitstun (s) (e.g. 0.2–0.4). During hitstun the enemy can’t move or attack and plays its hurt animation if that sprite frame exists.

R4. Make a thrown/shot projectile bounce off walls (slingshot stone) vs. break (arrow)

Weapons tab → select the ranged weapon → On wall hit → Rebound (bounces then settles on the ground) or Break (vanishes). Bullets/arrows use Break; a slingshot stone uses Rebound.

R5. Make an enemy shoot projectiles at the player

Edit Enemy Types → select type → attack editor → Add attack → set type Ranged, then set damage, range (trigger distance), cooldown, projectile speed, and an ammo sprite id. Enemy projectiles damage the player on hit.

R6. Make a “kill N enemies” quest (e.g. shoot 12 crows for Grandma)

  1. Quest State tab → add an integer variable, e.g. Crows_Killed (default 0), and a boolean like Crow_Quest_Done.
  2. Edit Enemy Types → the crow type → set Kill counter var = Crows_Killed, +amt = 1. Every crow death now increments it.
  3. Place the quest-giver NPC → Edit Instance Dialogue. Add a Condition node: Crows_Killed ≥ 12. On the “not yet” branch play reminder dialogue; on the “done” branch play completion dialogue plus an Action node that sets Crow_Quest_Done = true and gives the reward item.

Because everything reads/writes the same state registry, the counter persists and the dialogue branches react to it automatically. Nothing about “crows” is hard-coded — use any variable, threshold, enemy, and reward.

R7. Make defeated enemies stay dead — or respawn

Within a play session, staying dead is the default. To make an enemy respawn, enable the placement’s respawn flag in Edit Enemies, or the screen’s respawn enemies flag. Across launches nothing carries over — every launch is a new game (state initialized from defaults), so placed enemies always appear regardless of past kills.

R8. My newly-placed enemies don’t appear in game

Every launch now starts a new game (state initialized from defaults), so stale kills no longer hide placed enemies. If an enemy still doesn’t spawn, check: it has at least one path waypoint; its typeId matches a defined enemy type; and it isn’t walled off. (A leftover save.adstate is ignored unless you launch with --continue.)

R9. Make a shop NPC

Whether an NPC is a shop is a property of its NPC type, not the placement. The runtime reads interactionMode = type.defaultInteraction; there is no per-placement interaction override. A placement can only override the shop stock (shopInventoryOverride), never turn a non-shop type into a shop.

So:

  • Set up the shop on a type: Edit NPC Types → select/create a type → set default interaction = Shop → add inventory rows (project item id from the Items tab, buy price, sell price, stock count, unlimited flag).
  • Place it: Edit NPCs → place an instance of that Shop type. You may override its stock per instance for a one-off shop, but the type must already be Shop.
  • Don’t reuse a Talk/Quest type for a single shop NPC — changing that type to Shop makes every instance of it a shop. Create a dedicated Shop type instead.

In game, interacting opens a buy/sell screen; the player spends/earns Money and limited stock decrements on buy / increments when sold back.

Common mistake: setting a shop stock override on a placement whose type is Talk. The stock is saved but ignored — the NPC stays a talker (and if it also has no dialogue/graph it becomes non-interactive entirely). Fix by pointing the placement at a type whose interaction is Shop.

R10. Make branching dialogue / a choice

Place an NPC → Edit Instance Dialogue. Build the graph: Start → Dialogue nodes for lines, Choice nodes for player responses, Condition nodes to branch on state/inventory/money, Action nodes for effects (give/take item or money, set int/bool, heal/damage, move/hide/show/follow NPC, set animation, start/complete quest), and End. Use Validate to catch broken links and Simulate to walk the graph.

R11. Place an item / weapon / health pickup on a screen

Define the item in the Items tab (or use a built-in pickup type). Screens → select screen → Edit Items → place the pickup on the canvas. Selecting a weapon auto-fills the pickup’s on-map sprite from the weapon’s sprite. Walking over it collects it: weapons equip, health restores HP, and items/ammo go to the inventory + write ownership to the state registry.

Ammo lives in the inventory. A ranged weapon fires directly from the matching ammo item in your inventory (matched by the weapon’s ammo type); the inventory shows an AMMO section with each ammo’s sprite and count. There is no separate ammo pool — buying ammo from a shop or picking it up makes it immediately usable.

R18. Make an animated scenery tile (e.g. water, fire, a torch)

Animated tiles are ordinary palette tiles backed by a multi-frame sprite:

  • In screen graphics, select a region and Add Palette to add it to the Tile Palette (as you would any tile).
  • Click Edit Sprite on that palette row — the Sprite editor opens seeded with the tile’s image. Add frames (each frame becomes part of the loop) and save.
  • Back in screen graphics, hit the palette’s Refresh; the tile now shows “● anim (N)”. Select it and use the Stamp tool to place it on cells. An animated tile stamps as a runtime placement drawn on top of the screen at that cell (active layer decides order: Wall = in front of the player, Floor = behind). Right-click or Tile Erase removes a placement.

A single-frame tile stamps static pixels as before; it only animates once its sprite has ≥2 frames. Placements are saved into the chapter and animate in-game.

R12. Choose the playable character / edit its sprite

Characters tab → select a character → tick Playable Character (only one at a time). Click Edit Sprite to open its sprite sheet; assign frames with action types idle/walk /attack_1/etc. and facing directions. Return to Character saves and refreshes assignments.

R13. Make attack / hurt / death animations show up

In the Sprite Editor add frames labelled with the matching action type: player melee uses attack_1, ranged uses cast, taking damage uses hit_react, dying uses death; enemies use hurt and dead. The runtime switches action state automatically — you only need to supply frames with the right label (and optional per-direction variants).

R14. Add a new screen and link it

Screens tab → select the source screen → use the directional (N/S/E/W) controls to create/select a neighbour; links are written reciprocally. Paint its graphics with Edit Screen Graphics and edit its collision in Map Logic.

R15. Quickly test the screen I’m editing

Select the screen in the Screens tab and press Play Selected Screen. It launches fresh on that screen with full HP and all placed enemies present, without touching your save. Play From Last Entry resumes where you last entered a screen (needs at least one prior play so a checkpoint exists).

R16. Tune the combat “feel” globally

Per-type values (knockback resist, hitstun, aggro) are authored in Edit Enemy Types. Global feel — knockback strength, melee windup/active-window timing, rebound restitution, hit-flash duration, invulnerability frames — are constants at the top of src/game/engine.cpp (e.g. kMeleeWindupSeconds, kEnemyKnockbackBasePxPerSecond, kProjectileReboundRestitution) and require a rebuild.

R17. A placed NPC/enemy doesn’t appear, or doesn’t react

Work through these in order — they cover almost every case:

  1. The placement wasn’t saved. Creating a type (in Edit Enemy Types / Edit NPC Types) does not put anything on a screen. You must place an instance (Edit Enemies / Edit NPCs, in “Place” mode) and save the chapter. Verify a npc <id> <typeId> … / enemy … line exists for that screen after saving.
  2. Sprite id case / name mismatch. The runtime looks up assets/game/sprites/<spriteId>.sprite.json and the filesystem is case-sensitive. If the type’s sprite id is Silas but the file is silas.sprite.json, nothing draws. Make the sprite id match the file exactly (lowercase/uppercase included). Note sprite id takes precedence over characterId; characterId is only used as a fallback when sprite id is empty, and it resolves through assets/game/characters/<characterId>.adcharacter (which must exist).
  3. It appears but won’t interact (NPCs). Interaction is manual: stand close enough for the green prompt to show, then press E. The default interaction radius (24px) is small and measured center-to-center — raise it (~40–48) in Edit NPCs if the prompt never appears. Also confirm the NPC is actually interactable: a Talk/Quest NPC needs a dialogue graph or fallback lines, and a shop needs its type’s interaction set to Shop (see R9) — a placement-only stock override on a Talk type stays non-interactive.
  4. Enemy hidden by the defeated-enemy save. See R8 — use a fresh test launch or clear save.adstate.
  5. Walled off. Make sure the player can actually reach within the interaction radius; an NPC boxed in by solid mid-layer tiles can’t be approached.
